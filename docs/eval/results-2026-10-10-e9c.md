## History: 9 October 2026 — stopped at the offline proof (superseded by the run above)

The pre-registered offline proof (plan §19C.3, phase 2) has eight pass criteria. Seven held. One failed: the **cloud control did not fail offline**.

With `processLocally = false` and the network blocked, Chrome returned the correct transcript for the synthetic clips, in both locales. The cause was established afterwards, offline and with synthetic audio only (§19C.4):
- Once the English language pack is installed, Chrome 155 serves an English request on-device whatever `processLocally` says.
- It made no speech request at all.

The control could therefore not fail, by construction. The network block itself held throughout. The plan and the brief both say: if any proof item fails, stop, report, and process no DementiaBank audio. **E9-C is reported as not run.**
- No DementiaBank cut was served to Chrome.
- No hypothesis exists.
- `data/dementiabank/` holds no Chrome cache.

Whether to amend the control and run is the author's decision (§19C.6).

## 19C.4 Why the cloud control did not fail (`chrome-ondevice-cloud-diagnostic_4a92057.json`)

This diagnostic was run after the stop, offline, with synthetic audio only. Its purpose is to explain the failure; it does not reverse it. One harness Chrome, with the same guards, ran five steps 5 s apart. The proxy requests and NetLog URLs are attributed to each step by its time window.

| Step | Transcript | Error | Result events | Proxy requests in the window | NetLog URLs in the window |
|---|---|---|---|---|---|
| en-NZ, `processLocally = true` | correct | — | 29 | accounts.google.com (background) | `accounts.google.com/ListAccounts` |
| en-NZ, `processLocally = false` | **identical** | — | **29** | android.clients.google.com (background) | `android.clients.google.com/c2dm/register3` — **no speech request** |
| fr-FR (no pack), `processLocally = false` | none | **`network`** | 0 | **2 × `CONNECT www.google.com:443`, refused** | **`www.google.com/speech-api/full-duplex/v1/up` and `/down`** |
| fr-FR (no pack), `processLocally = true` | none | `language-not-supported` (then the 20 s end cap) | 0 | update.googleapis.com, mtalk.google.com (background) | component-update check |
| en-NZ, `processLocally = false`, second clip | correct | — | 22 | clients1.google.com (background) | `clients1.google.com/tools/pso/ping` |

Reading:
- **With the English pack installed, Chrome 155 serves an English request on-device even when `processLocally` is false.** It makes no attempt at the cloud: there is no speech URL and no `www.google.com` connection in those windows. The result events match the on-device request one for one.
- So the pre-registered same-locale control could not fail, whether or not the network was blocked. Its failure is a property of Chrome, not a leak.
- **The cloud path is blocked.** Where Chrome does use the cloud (French, with no pack), it tries Google's speech endpoint (`/speech-api/full-duplex/v1/up` and `/down`). The local proxy refuses it, and the recogniser reports `network`.
- **The detector works.** The NetLog speech-URL rule, a stop rule in the run, catches exactly that attempt (8 NetLog events).
- No external socket, no external flow, no sandbox denial and no microphone request occurred in the diagnostic either.

What this does not show: whether Chrome also prefers the installed pack when it is **online**. The network stays off outside the install phase, so this was not tested.

## 19C.5 Deviations and limitations

- **Kernel-level network block not used.** A `sandbox-exec` profile denying non-loopback connections worked for curl. Chrome's own sandbox cannot start inside it, and the disabled-sandbox flag it would need was refused by a safety check. The proxy and resolver rules, with the five monitors, are the block, as the brief specifies. Chrome ran under the profile twice on `about:blank` before the plan was committed (§19C.1).
- **Background traffic.** Even with `--disable-background-networking`, Chrome requests Google endpoints at start-up and periodically. In the offline phases all such requests were refused locally. The run's stop rule would have held the session to the proof's baseline of these.
- **Not run:** the DementiaBank pass in both locales, the robustness re-run, and every WER, CI, paired comparison and expectation (C1–C4). C1–C4 are untested; none is supported or refuted.
- If the run goes ahead later, the limitations the plan anticipates still apply:
  - the proxy label (on-device, not the app's cloud service);
  - files streamed as a track, not a live microphone;
  - an in-page track with none of Chrome's capture processing;
  - a US-English corpus;
  - and, from the install, **en-NZ and en-US run the same en-US model**.

The pre-registered control could not fail once the pack was installed, so it does not test what it was meant to test, namely that the cloud path cannot work offline. A control that can fail exists. If the author agrees, a dated amendment would be committed **before any DementiaBank audio**:
1. **Replace** the same-locale cloud control with a **cloud control in a locale that has no installed pack** (fr-FR, a synthetic French clip, `processLocally = false`). Offline it must fail with `network`, and the NetLog must show the speech endpoint refused by the local proxy. §19C.4 shows exactly this.
2. **Add an on-device-path check to the proof:**
   - the en-NZ request with `processLocally = false` makes no speech request (no speech URL, no `www.google.com` connection in its window);
   - every English request in the run is made with `processLocally = true`, which `language-not-supported` shows is refused rather than sent to the cloud when no pack exists.
3. **Re-run the offline proof** under the amended criteria, then the run as pre-registered: en-NZ first, k = 4, headless, the same stop rules. The speech-URL rule is now shown to work.

Everything else in the plan would stay as written. The harness profile with the installed pack is in the session scratch directory. Re-installing takes about 20 s.
